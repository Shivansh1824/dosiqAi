The "Medication Clustering" Strategy

The Problem

Imagine you have to take 3 different medicines at exactly 8:00 AM.

Currently: Your phone buzzes 3 separate times. Your screen gets cluttered with 3 separate banners. If you miss them, you get 3 separate follow-up reminders. It’s chaotic, noisy, and annoying.

The Solution: "Clustering"

Instead of treating them as 3 separate events, we group them into one single "8:00 AM Event".

Think of it like a School Bus:
Instead of 30 parents driving 30 cars to drop kids at school (Traffic Jam!), uses one Bus to pick everyone up at the same time. The "Bus" is our Cluster Notification.

How it works for the User:

  • At 8:00 AM: You get ONE notification.
  • The Message: It says "Time to take Aspirin, Vitamin D & 1 other."
  • The Action: You tap it, and see a list of all 3 medicines to check off.
  • The Reminder: If you take some and uncheck/leave others, we treat the unchecked ones as Skipped. The cycle ends there. No extra nagging.

Technical Architecture In-Depth

1. Offline-First Reliability:
The system uses an "Unrolled Schedule" approach. Instead of checking logic at the exact moment of the alarm (which might fail if the app is killed), we pre-calculate the schedule for the next 14 days and register it with the device OS immediately. This means even if the user goes offline or force-closes the app, the "Smart Cluster" notifications will still fire correctly.

2. The Interval Math (The "Active Check"):
For every active medication, we perform exact math: (TargetDate - StartDate) % Interval == 0. This guarantees mathematically correct skipping logic (e.g., for "Every 3 Days" meds) without complex database queries.

3. Data Integrity Payload:
Each cluster notification carries a hidden payload: activeMedicationIds: [...]. This ensures that when the user taps the notification, the UI receives the exact list of medications that were calculated for that specific instance, regardless of subsequent schedule changes. This is our "Rock Solid Foundation".

4. Slot Management & Horizon Safety (The 64 Limit):
iOS limits app notifications to 64 slots. If a user has a heavy schedule (e.g., 6 doses/day), a 14-day loop (84 slots) would overflow the system.
Why this is dangerous: When the limit is hit, iOS doesn't just stop; it often deletes the earliest notifications (like tomorrow's alarm) to make room for the new ones (14 days away). This is called "FIFO Drop" and causes missed doses.
The Fix: We implemented a Dynamic Safety Valve that auto-shrinks the horizon (e.g., from 14 days to 8 days) for heavy users. This guarantees we stay UNDER the limit (48 < 64), ensuring tomorrow's alarm is 100% safe.

The "Unified Reminder". The logic is now fully integrated with the UI actions.
