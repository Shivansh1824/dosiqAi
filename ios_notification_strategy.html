🚨 The Challenge: Why Native Fails Us

You might ask: "Why not just set a repeating follow-up like Android?"

1. The "Infinite Loop" limitation

iOS handles repeating notifications differently. If we set a native repeat for a follow-up (e.g., "Repeat every 5 mins"), it runs forever until cancelled manually. We cannot say "Repeat 3 times then stop".

Result: If the user ignores the phone, the follow-up would ring every 5 minutes for eternity, draining battery and annoying the user.

2. The "64 Limit" Constraint

iOS enforces a strict hardware limit of 64 Pending Notifications PER APP (Total). Not per medication.

If we try to manually schedule "3 follow-ups per dose" for 5 medications for the next month, we would need 450+ slots. We only have 64.

Result: The system would silently discard reminders, leading to critical failure (missed meds).

Conclusion: We cannot use simple Native Repeating (too annoying) OR simple Manual Scheduling (hits 64 limit). We need a smarter way.

🚀 The Solution: "Hybrid Engine"

We solve this by splitting the problem into two layers:

  • The Shield (100% Reliable): Uses iOS RepeatFrequency.DAILY. It only uses 1 Slot per med. It guarantees the primary alarm always rings, even offline.
  • The Smart Layer (Experience): We manually schedule just the next 3 days of follow-ups using the remaining slots. We "refill" this bucket every time the user opens the app OR interacts with a notification (Taken/Skip).

🔄 2.5 Auto-Refill Mechanics

"How does the infinite loop continue if we only schedule 3 days?"

The "Bucket Refill" happens automatically in two scenarios:

Scenario A: App Launch (Foreground)

Every time the user opens the app to check their progress or dashboard, the logic engine runs instantly. It calculates missing follow-ups for the next 3 days and fills the slots.

Scenario B: Notification Action (Background)

When a user taps "Taken" or "Skip" on a notification:

  1. iOS wakes up the app in the Background.
  2. The system grants approx. 30 seconds of execution time.
  3. Our "Refill Engine" runs silently, calculates the next 3 days of follow-ups, and schedules them via UNUserNotificationCenter.
  4. We call the completion handler to finish the task.
Result: As long as the user engages with the app or the notifications, the schedule is infinite.

⚙️ 4. Technical Safeguards (The "Rock Solid" Parts)

A. Dynamic Safety Valve 🛑

What if we hit the 64 limit?

The code dynamically counts slots before scheduling. If count >= 63, it STOPS scheduling follow-ups and instead schedules a single "Refill Reminder". The app never crashes; it just asks for a sync.

B. The "Cluster Kill" 🧹

What about notification pile-up?

When user taps "Taken" on ANY notification (Primary or Follow-up), our code instantly hunts down all related IDs (siblings) and wipes them from the lock screen using the IOS API removeDeliveredNotifications(withIdentifiers:).
